Effect Boundary Adoption

The API layer has 109 route files, 55 direct JSON body readers, and 20 asserted request bodies — but zero Effect imports at the API boundary. Routes each hand-roll parsing, validation, error mapping, and response serialization. The goal is a shared Effect request runner that gives every route typed schema decoding, tagged domain errors, structured logging, and cancellation — without wrapping existing try/catch code.

01

Problem

The codebase has a stated architectural goal of adopting Effect throughout, but the API boundary — the most security-sensitive and contract-enforcing layer — has seen zero adoption. The numbers:

ArtifactCountConsequence
Route files109Each independently handles parsing, errors, and response shape
Direct JSON body readers55No schema-based decoding; each reads the body manually
Asserted/cast request bodies20Runtime-type-unsafe — a malformed request passes through as unknown
Effect imports in route modules0No Schema, no tagged errors, no typed request handling
Record-based response mappingMultipleError codes are cast-only strings; no compile-time error tag verification

Every route that hand-rolls request parsing reintroduces the same class of bugs: missing field validation, incorrect type narrowing, inconsistent error responses. Together, the 109 routes effectively have 109 different ways to be wrong.

02

Execution plan

Core approach

Build one small Effect request runner that Next.js route handlers call into. Route modules remain thin Next.js adapters that extract the request, pass it to the runner, and return the serialized response. The runner handles schema decoding, authentication context, service layer wiring, tagged errors, cancellation, structured logging, and HTTP serialization.

Critical rule: Do not wrap existing try/catch code in Effect. Replace it with typed ops and delete the old branch in the same domain change.

Shared runner contract

The runner provides these guarantees once, for every route:

  • Schema decoding: Incoming request body is decoded through an Effect Schema at the boundary. Adversarial, missing, or malformed data produces a stable, typed error response — not a cryptic 500.
  • Authentication context: Session and workspace context are extracted once and passed as typed context to the handler.
  • Tagged errors: Every domain error has a stable string tag mapped to an HTTP status code. Routes cannot accidentally leak provider error messages.
  • Cancellation: The Next.js request AbortSignal is threaded through the Effect runtime.
  • Structured logging: Request ID, route, duration, and error tag are logged uniformly.
  • Response serialization: Success and error payloads follow one schema.
03

Benefits & estimated improvement

Uniform error behavior All 109 routes produce the same error shape, same status code mapping, and no accidental provider message leaks. Error handling is written once in the runner.
Eliminate parsing bugs 55 hand-rolled JSON readers and 20 asserted bodies become 0. Schema guarantees every route receives exactly the type it expects.
600–1,200 fewer lines Duplicated parsing, guards, casts, and response mapping are deleted domain by domain. Each domain change replaces a larger legacy surface with a smaller runner invocation.
Auditable contracts Each route's input schema and error tags are explicit and inspectable. Security review becomes reading the schema file, not tracing through hand-written property probes.

Codebase readability impact: Very high. The current API layer is 109 independent implementations of the same concept (parse request → validate → call service → map response). A future developer landing on a route file will see a 5–15 line adapter that declares its input schema, invokes the runner, and maps domain errors to public ones — instead of 50–100 lines of hand-rolled parsing, try/catch blocks, and ad-hoc response construction. The schema files become the source of truth for API contracts. Domain errors are discoverable in one tagged union per domain rather than spread across 55 readers as string-throwing code paths.

Performance impact: Negligible. Schema decoding adds a one-time parse cost per request, which is dominated by downstream service calls (database queries, model inference). The runner itself adds no measurable overhead. Cancellation propagation through Effect may actually reduce wasted work on aborted requests.

04

Risks & stop conditions

RiskResponse
A second permanent API framework appears alongside EffectStop domain migration and simplify the runner before continuing. Only one framework can survive.
Untyped escape hatches increase (e.g. any casts in route files)Add a lint rule forbidding as any in route handlers. Audit each domain migration for unintended casts.
Schema overhead is measurable in high-throughput routesBenchmark Schema decode vs. hand-rolled JSON.parse + typeof checks. Add caching for repeated schemas.
Route file churn causes merge conflictsMigrate one domain at a time, each in a focused PR. Coordinate with active feature branches.
Stop condition If migration velocity is less than one domain per week after the first two domains, reassess scope. The full 6-domain migration is viable at ~1 domain/week; slower suggests the runner needs simplification.
05

Validation

  • Each domain migration: all existing tests pass without modification to test assertions (response shape should not change).
  • Schema decoding coverage: every schema has positive (valid input → decoded) and negative (invalid input → tagged error) tests.
  • Effect contract snapshot for each domain: status codes, public error tags, cancellation, and provider-error redaction are documented.
  • Before/after p50/p95 latency for migrated routes confirms no regression.
  • No any casts remain in migrated route files (verified by lint).
  • Legacy runner helpers and duplicate error mappers are deleted after the final domain.

Estimated code delta: +600 to +1,000 added, −1,200 to −2,200 deleted. 4–7 weeks engineering time.
