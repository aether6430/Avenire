Credit & Billing

Two billing findings: credit admission uses a non-locking read/compute/write pattern so concurrent chats can undercount usage (BILL-01); and Polar native credits can replace the custom refill ledger, deleting roughly 400 lines of manual debit/refund logic while still requiring local admission and durable event delivery (BILL-02).

01

Problem

BILL-01 — Non-atomic credit admission

The current credit check at billing-data.ts:307 follows a read-balance → compute-remaining → write-new-balance pattern without a locking invariant. Under concurrent requests — which is normal for a chat application — two requests can read the same balance, both compute that they have enough remaining, and both write back, leaving a balance that reflects only one deduction. Credits are systematically undercounted.

BILL-02 — Custom refill ledger duplicates Polar

The codebase maintains its own refill/debit/restore ledger in billing-data.ts:254 and schema.ts:795. Polar natively supports credits-only meters, subscription-cycle grants, event ingestion, and customer meter balances. However, Polar explicitly does not block usage at zero balance (credit enforcement is the caller's responsibility), and Polar events are immutable. So Avenire must keep local admission enforcement and idempotent delivery — but the custom ledger itself can be replaced.

02

Execution plan

Phase 1 — Fix credit atomicity (3–4 days)

Introduce row-level locking on the balance read to prevent concurrent undercounting.

  • Add SELECT ... FOR UPDATE (or the database equivalent — e.g. pg_advisory_xact_lock or a pessimistic lock on the balance row) before computing remaining credit.
  • Keep the read and write in the same database transaction under the same lock.
  • Alternatively, use an atomic UPDATE ... SET balance = balance - ? WHERE balance >= ? and check affected rows. This is simpler and works for the debit case if no other state needs to be read under lock.
  • Add a concurrency stress test that proves the fix: 50 simultaneous requests against a balance of 25 credits should produce at most 25 successful admissions.
This phase is worthwhile independently Even without the Polar migration, atomic credit admission closes a correctness bug that directly costs revenue.

Phase 2 — Polar credits migration (4–8 days)

Replace the custom refill ledger with Polar-managed credits. The target flow:

1. Local atomic reservation→ 2. Durable outbox event→ 3. Worker sends to Polar→ 4. Reconciliation

Step-by-step

  • Reservation: The admission check from Phase 1 now reserves against a locally mirrored balance (still atomically). The mirrored balance is updated optimistically — the source of truth remains the Polar grant + local events until delivery.
  • Outbox: A durable usage-event outbox table records each consumption event with a stable idempotency key. Written in the same transaction as the reservation.
  • Worker: An async process reads undelivered events, sends them to Polar's event ingestion API, marks them delivered, and retries on transient failure with exponential backoff.
  • Reconciliation: Periodic comparison between local reservation totals and Polar customer-meter balances. Alerts on divergence exceeding a configurable threshold.

What gets deleted

  • Custom refill schedule logic (grant scheduling, subscription-cycle alignment).
  • Manual debit and refund functions — Polar's event ingestion handles credits as immutable events.
  • Entitlement checks that duplicate Polar's customer-meter state.
  • The usage_meter table if Polar completely replaces it (confirm dashboard needs first).

The audit found that the test suite has no billing characterization coverage and does not emulate Polar retries, concurrent credit admission, or balance divergence. New tests are essential for this migration even under a strict "no new tests" constraint.

03

Benefits & estimated improvement

Accurate credit accounting Atomic admission eliminates concurrent undercounting. Every chat session deducts exactly once.
~400 lines deleted Custom refill, debit, and refund logic replaced by Polar credits. The local surface shrinks to reservation + outbox + reconciliation only.
Polar-managed grants Subscription-cycle credit grants, meter accumulation, and customer balance are handled by Polar. No more manual grant scheduling.
Resilient admission Admission stays local and synchronous (no network call to Polar on the chat hot path). A Polar outage does not block usage — it only delays event delivery.

Codebase readability impact: High. The billing module currently mixes several concerns — grant scheduling, debit, refund, entitlement checks, and manual Polar calls — across overlapping functions and a dedicated schema table. After the migration, billing becomes three clearly separated layers: (1) a thin local admission layer (atomic reservation), (2) a durable outbox for event delivery, and (3) reconciliation. The Polar SDK handles grant lifecycle, which removes 400+ lines of custom scheduling and arithmetic that had to be tested, audited, and maintained. Developers reading the billing module will see a linear flow — reserve → emit → send → reconcile — instead of a web of cross-cutting debit/refund/restore logic.

Operational improvement: Polar's dashboard becomes the UI for customer credit balances and grant schedules. No more internal admin tools needed to manually adjust balances or inspect the refill ledger.

05

Validation

  • Phase 1: Concurrent admission stress test — 50 simultaneous requests against 25 credits produce ≤ 25 successful admissions, and the final balance is exactly 0.
  • Phase 2: Outbox delivers events to Polar under normal operation, retry, and Polar API failure. Idempotency key prevents duplicate entries.
  • Reconciliation detects injected divergence (simulated local/Polar mismatch) and alerts.
  • Shadow mode: run old and new billing paths side-by-side. Compare balances daily for one week before cutover.
  • Performance: confirm zero network calls to Polar on the chat hot path (admission is local-only).
  • Refund and renewal scenarios behave identically before and after migration.

Estimated code delta: +350 to +540 added, −650 to −1,020 deleted. 7–12 days engineering time.
