Upload Security & MIME Policy

Three findings that together erode the trust model around binary uploads: preflight results are discarded and client-controlled metadata is accepted; multipart sessions accept 10,000 × 16 MiB parts without cumulative accounting before assembly; and MIME policy is duplicated, contradictory, and persists wildcard types. The fix is a single upload capability flow backed by one canonical file contract.

01

Problem

SEC-01 — Preflight session not bound to upload

The preflight endpoint returns a session that validates owner, workspace, and expected metadata. However, the client discards this result at explorer.tsx:3992 and submits caller-controlled key, URL, MIME type, and file size through legacy registration. Trust moves from the server-owned preflight session back to the client.

SEC-02 — Multipart accounting gapped

The multipart session model accepts up to 10,000 parts at 16 MiB each without tracking cumulative bytes or total part count during ingestion. Size validation only happens after assembly and provider upload. A client can stream 160 GiB of parts before any rejection occurs.

FILES-01 — Duplicated, contradictory MIME policy

MIME type validation exists in at least two places (upload-registration-model.ts:21 and ingestion/src/utils/media.ts:3) with different allowlists. Wildcard types like video/* can be persisted. File and workspace identifiers remain interchangeable strings with no branded types. Expected error codes use cast-only patterns.

Security impact The preflight trust gap means a malicious client can register arbitrary metadata, bypass size limits, and store files under any MIME type regardless of content. This is the highest-priority operational risk in the audit.
02

Execution plan

Phase 1 — File contract (5–8 days)

Before fixing the upload flow, define a shared contract used by all boundaries: web routes, database adapters, upload runtime, and ingestion.

ConcernTarget
IdentifiersBranded WorkspaceId, StudentFileId, UploadSessionId, StorageKey
MIME typesSingle concrete allowlist reconciled across declared type, file extension, and detected magic bytes
ErrorsTagged domain errors mapped once to stable status code and public payload
ValidationEffect Schema at every external boundary; no hand-written property probing in business logic

Adversarial coverage: null bytes, path traversal, confusable/double extensions, malformed part order, invalid sizes and checksums, expired sessions, duplicate completion, cross-workspace ID substitution.

Bounded content inspection (signature mismatch, archive depth, decompression risk) happens separately — Schema cannot prove binary content safety.

Phase 2 — Upload capability (4–7 days)

The upload session becomes the sole server-issued capability. The flow changes from:

Preflight→ Client picks key, URL, MIME, size→ Provider upload→ Registration (client metadata)

To:

Preflight → bound session→ Client provides: session ID + parts→ Server enforces: aggregate bytes, part count, per-part size, order, checksum, expiry→ Assembly (server-authorised)→ Idempotent completion + registration

Key changes

  • Return one opaque session identifier from preflight; require it at every write and completion step.
  • Enforce cumulative byte and part-count limits incrementally — reject before assembly, not after.
  • Make completion idempotent; consume the capability exactly once inside the same transaction that registers the file.
  • Delete abandoned parts, failed provider objects, and legacy registration fields that accept a caller-selected key or URL.
  • Return only opaque file identity and safe metadata to the client.
03

Benefits & estimated improvement

Closed P0 security hole Preflight results can no longer be discarded. The server controls final metadata, size, and storage identity.
Early rejection Multipart overruns are caught before expensive assembly and provider writes. Rejection latency drops from minutes to milliseconds per part.
Single trust boundary One linear state machine replaces the current preflight + separate trust path. Fewer places for bugs to hide.
Canonical MIME policy No wildcard persistence, no contradictory allowlists. Ingestion and web share one source of truth.

Codebase readability impact: High. The upload path becomes a single coherent state machine in one area of the codebase instead of split across preflight, client-side registration, and server-side validation that accidentally contradicts itself. Branded identifiers make it impossible to accidentally swap a workspace ID for a file ID — type safety catches cross-boundary mistakes at compile time. The MIME allowlist in one place means changing supported types touches one file, not two that may already disagree.

Security improvement: Attenuated capability means a compromised client session cannot write files outside the owning workspace's key prefix, cannot set an arbitrary MIME type, cannot exceed the pre-authorized byte budget, and cannot replay a consumed session. The provider-stored object's key is server-determined rather than client-supplied, eliminating storage key injection.

05

Validation

  • Upload fixtures covering: ownership substitution, aggregate exhaustion, duplicate completion, checksum mismatch, MIME spoofing, and cleanup.
  • Negative tests for cross-workspace session use and expired session replay.
  • Idempotent completion: duplicate requests after success produce the same result and do not create duplicate records.
  • Provider object cleanup test: abandoned parts are swept within the configured TTL.
  • MIME allowlist verification: wildcards are rejected, both allowlists agree, magic-byte detection matches declared type.
  • Throughput benchmark: per-part validation overhead measured and documented.

Estimated code delta: +550 to +950 added, −1,000 to −1,700 deleted. 9–15 days engineering time.
