Retrieval Performance

Three performance findings that together make retrieval 10× slower than necessary. Redis has a 10-second connection timeout and blocks the entire request before search begins. The slow path repeats the fast embedding and hybrid search, while independent expansion and HyDE steps are serial. The cache fingerprint requires hashing an ordered aggregation of the entire workspace corpus — even cache hits scale with corpus size.

01

Problem

PERF-01 — Redis timeout blocks all search

The Redis client has an exact 10-second connection timeout. Retrieval awaits this connection before any search work begins. When Redis is slow or unreachable, the entire request hangs for 10 seconds before falling back. Failed clients are retried per-request with no cooldown or circuit breaker.

This directly matches the reported latency pattern. Production timing traces are needed to confirm, but the code path makes the correlation highly probable.

PERF-02 — Serial redundant computation

The slow retrieval path (at retrieve.ts:960) repeats the fast embedding and hybrid search work instead of reusing results. Meanwhile, expansion and HyDE — two fully independent branches — are executed serially despite having no dependencies on each other.

PERF-03 — Cache fingerprint scales with corpus

Every cache lookup (at ingestion-data.ts:542) first hashes an ordered aggregation of the entire workspace corpus. This means even a cache hit has to read and hash O(corpus) data before it can confirm the cache is valid. For large workspaces, this cost alone may exceed the cache lookup benefit.

02

Execution plan

Step 1 — Instrument phase timings

Before any optimisation, emit structured timings for each retrieval phase: cache connect, cache lookup, embedding, lexical search, vector search, fusion, expansion, HyDE, reranking, response shaping. This confirms which phase dominates and establishes the baseline for measuring improvement.

Measurement first The 10-second Redis timeout is the strongest candidate, but production traces may reveal a different bottleneck. Do not optimise based on code reading alone.

Step 2 — Fix Redis connection (PERF-01)

  • Reduce the connection timeout from 10s to 2s. This bounds worst-case cache latency to 2s instead of 10s.
  • Add a cooldown period (e.g. 30s) after a failed connection attempt: do not retry Redis on every request during an outage.
  • Implement a lightweight circuit breaker: track consecutive failures and skip Redis entirely for a recovery window, then probe once.
  • Ensure the retrieval path starts search work immediately rather than awaiting the Redis connection before proceeding. Cache result is best-effort enrichment, not a gate.

Step 3 — Parallelise independent work (PERF-02)

  • Launch expansion and HyDE concurrently with Promise.all (or the Effect equivalent: Effect.all with {concurrency: 2}).
  • Pass one shared AbortSignal through the retrieval tree; cancel unused branches when sufficient results are found.
  • Reuse the initial embedding and fast hybrid candidate results in the slow path instead of recomputing them from scratch.
  • Target: eliminate the serial expansion + HyDE gap (currently 2× the slowest branch's wall time).

Step 4 — Fix cache fingerprint (PERF-03)

  • Replace the O(corpus) ordered content hash with an indexed workspace ingestion revision: a simple monotonically increasing counter (lastIngestedAt or contentVersion) stored on the workspace record.
  • On every ingestion event, bump the revision. The cache key becomes cache:query:{workspaceRevision}:{queryHash}.
  • This reduces cache validation from O(corpus) content read to a single indexed integer lookup — effectively constant time.
  • Trade-off: cache invalidates more eagerly (any ingestion busts all query caches for that workspace). Acceptable because ingestion is far rarer than querying for most workspaces. Add a staleness-tolerant option if needed.

Step 5 — Segment timing data

After changes, collect per-phase timings and compare against the baseline. Document p50/p95 for each phase. Keep recall and citation-quality evaluations as release gates.

Redis resilience 2s timeout, cooldown, and circuit breaker prevent a cache outage from becoming a full retrieval outage. Failed clients are not retried without rest.
Parallel expansion Serial HyDE + expansion becomes concurrent. Wall time for these two steps drops from sum-of-both to max-of-both — typically a 1.5–2× speedup for that segment.
Constant-time cache validation O(corpus) full-content hash → O(1) revision counter. Large workspaces see the most dramatic improvement: cache hits no longer require reads proportional to corpus size.
No duplicated model calls Reusing initial embedding and hybrid candidates in the slow path removes redundant model inference, reducing cost and latency equally.

05

Validation

  • Retrieval traces with Redis healthy, slow (e.g. 3s latency), and unavailable (connection refused). Compare p50/p95 latency, recall, citation quality, and call counts.
  • Phase timing output matches expected structure and reveals the dominant bottleneck.
  • Cache hit/miss ratio before and after revision-based fingerprint. Confirm no false cache hits from stale data.
  • Expansion + HyDE timing: confirm serial-to-parallel improvement matches max(branch) instead of sum(branches).
  • No duplicated embedding calls in slow path (verify via call counters).
  • Circuit breaker: inject 5 consecutive Redis failures, confirm Redis is skipped for the cooldown window, then probed exactly once after recovery.
